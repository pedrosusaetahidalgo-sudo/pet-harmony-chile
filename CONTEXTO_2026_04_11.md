## 5. NUEVAS INICIATIVAS — back-to-end + UX de navegación 🎯

> El dueño quiere **que back-to-end no falle en ningún punto** y que **el flujo de menús/redirecciones sea intuitivo y memorable**.

### 5.1. Iniciativa A — Hardening backend (zero-failure)

**Objetivo**: garantizar que cualquier acción del usuario nunca tire 400/500 silencioso, RLS roto, FK rota o data corrupta.

**Trabajo a hacer en próxima(s) sesión(es)**:

1. **Audit de queries con joins PostgREST**
   - Buscar todos los `select(\`*, X:fk(...)\`)` en `src/`
   - Verificar que cada FK existe en la DB con migración
   - Para los que no, refactorear a fetch separado (como ya hicimos con `adoption_posts` en Maps)
   - Comando: `grep -rn "select.*:.*(" src/ | grep -v node_modules`

2. **Audit de RLS por tabla**
   - Listar las ~80 tablas de Supabase
   - Para cada una, confirmar policy de SELECT/INSERT/UPDATE/DELETE coherente con el rol que la usa
   - Especial atención a: `posts`, `pet_activities`, `vet_bookings`, `service_promotions`, `paw_point_transactions`, `external_calendar_events`
   - Generar reporte con `policies_audit.sql` y dejarlo en `supabase/audits/`

3. **Audit de edge functions con error handling**
   - Las 17 functions: revisar que ninguna tire `throw error` sin `try/catch`
   - Asegurar que todas devuelvan JSON estructurado en error (no HTML, no texto plano)
   - Agregar logging con `logger.error` consistente

4. **Audit de transacciones críticas (pagos + premium)**
   - `flow-create-subscription` + `flow-webhook` + `apply_premium`: verificar idempotencia end-to-end
   - Test manual: pago duplicado → debe ser idempotente
   - Test manual: pago en mascota 2 sin Premium → debe bloquearse

5. **Sentry / error tracking**
   - Considerar agregar Sentry para capturar errores en producción que el usuario no reporta
   - Free tier: 5k events/month es suficiente

6. **Reconciliación de `total_paw_points` agregado**
   - El fix actual de `awardPoints` lo actualiza pero no es atómico
   - Crear migración con un trigger AFTER INSERT en `paw_point_transactions` que actualice `user_guardian_progress.total_paw_points` desde la suma real
   - Eso elimina la posibilidad de drift

### 5.2. Iniciativa B — Navegación intuitiva y memorable

**Objetivo**: que cualquier dueño chileno no técnico pueda usar la app sin pensar en dónde está cada cosa. Hoy hay drawer + bottom nav + breadcrumbs implícitos + 43 rutas con redirecciones inconsistentes.

**Trabajo a hacer en próxima(s) sesión(es)**:

1. **Auditar jerarquía de rutas vs jerarquía mental del usuario**

   Hoy las rutas están mezcladas:
   - `/home` `/my-pets` `/add-pet` `/medical-records` (Salud)
   - `/veterinarios` `/servicios` `/mis-reservas` `/maps` (Servicios)
   - `/feed` `/actividad` `/chat` `/adoption` `/paw-game` (Comunidad)
   - `/provider/dashboard` `/provider/profile-edit` (Profesional)
   - `/upgrade` `/profile` `/settings` (Cuenta)

   Pero algunas rutas no respetan esa jerarquía. Ej: `/maps` está en Servicios pero sirve también para mascotas perdidas (Salud) y adopciones (Comunidad).

   **Tarea**: redibujar la jerarquía con el dueño y reorganizar rutas + sidebar para que coincida.

2. **Definir las "5 acciones fundamentales" del usuario y darles tab fija**

   Propuesta de bottom nav permanente (5 tabs):
   - 🏠 **Inicio** (`/home`)
   - 🐾 **Mascotas** (`/my-pets`)
   - 🏥 **Vet** (`/veterinarios` → directorio público)
   - 🔔 **Recordatorios** (`/reminders` — falta crear si no existe)
   - 👤 **Perfil** (`/profile` o `/settings`)

   El resto va en drawer/menú secundario. Esto coincide con el modelo de apps que el dueño chileno YA conoce: WhatsApp, Instagram, MercadoPago.

3. **Reglas de redirección consistentes**

   Hoy hay inconsistencias:
   - Usuario logueado en `/` → ve landing pública (debería redirigir a `/home`)
   - Logout → va a `/auth` (correcto)
   - Login con `returnTo` → restaura ruta original ✅
   - 404 → ¿qué pasa? hoy es la landing del SPA, debería ser un 404 amigable (Prompt 9 pendiente del 04-10)

   **Tarea**: documentar las reglas en `src/lib/routing.ts` y aplicarlas en `App.tsx` con un wrapper consistente.

4. **Breadcrumbs visibles en pantallas profundas**

   Ej: `/pet/<id>/clinical?tab=resumen` no tiene breadcrumb. Usuario no sabe dónde está. Agregar `<Breadcrumbs>` arriba de los headers de página en rutas con > 2 niveles.

5. **Atajo "volver" coherente**

   Hoy algunas pages tienen `<ArrowLeft onClick={() => navigate(-1)}>` y otras no. Uniformar: todas las páginas que no son tabs principales tienen el botón en el header.

6. **Empty states con CTA específico**

   Hoy varios empty states genéricos ("Sin resultados") no le dicen al usuario qué hacer. Cada empty state debe tener una acción clara: "Crear primer recordatorio", "Ver veterinarios cerca", etc.

7. **Onboarding contextual de primera visita**

   Hoy hay `OnboardingTutorial` en `/feed` pero no hay onboarding para `/home` ni `/my-pets`. Crear flow de 3 pantallas la primera vez que un usuario nuevo entra:
   - "Agrega tu primera mascota"
   - "Programa tu primer recordatorio"
   - "Encuentra tu veterinario"

8. **Tests de usabilidad**

   Una vez aplicado todo lo anterior, grabar otro video de QA pero esta vez navegando como un usuario nuevo desde 0 (sin guía). Identificar dónde se "pierde" el usuario.

## 11. Decisiones clave en memoria persistente

`~/.claude/projects/.../memory/`:
- `project_flow_payment_gateway.md` — Premium B2C usa Flow, NO Webpay
- `feedback_secrets_in_chat.md` — Si el dueño pega API keys, advertir + rotar + nunca commitear (aplicó 4+ veces)
- `feedback_chilean_spanish.md` — Toda copy en tuteo chileno

**Nuevas reglas a memorizar (esta sesión)**:

1. **`git add -u` ≠ `git add docs/`** — `-u` solo trackea modificados, NO agrega archivos nuevos. Después de cada `npm run build` que genera nuevos chunks con hash, hay que usar `git add docs/` también, o el deploy queda con 404 en chunks. Aplicó 1 vez (commit `1c69396`).

2. **react-leaflet 5.x requiere React 19** — Si en algún momento se intenta upgrade a React 19, ojo. Mientras estemos en React 18, mantener react-leaflet 4.x.

3. **Build script no debe sobreescribir 404.html** — `public/404.html` tiene el redirect SPA correcto. Vite lo copia a `docs/404.html` al hacer build. Cualquier paso post-build que toque `404.html` lo rompe.

4. **Joins PostgREST con FK** — Usar `select("*, x:fk(...)")` SOLO si la FK existe en la DB y PostgREST la auto-detectó. Para tablas como `adoption_posts` donde la FK no está, hacer fetch separado y join en cliente.
